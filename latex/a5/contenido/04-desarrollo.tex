\section{Desarrollo del trabajo}

Este capítulo documenta el proceso completo de instalación, configuración y
prueba de dos servicios fundamentales de la infraestructura de red del
proyecto: el servidor DHCP implementado con Kea y el servidor web
implementado con Nginx, ambos sobre el sistema Debian del proyecto. Se
describe desde la instalación de los paquetes necesarios hasta las pruebas
de asignación automática de direcciones IP y las verificaciones de acceso
web realizadas desde los equipos clientes.

% ============================================================================
\section{Servidor DHCP}

El servidor DHCP se implementó utilizando Kea, el servidor DHCP de ISC
(\textit{Internet Systems Consortium}) y sucesor del clásico
\texttt{dhcpd}, seleccionado por su soporte activo, su configuración basada
en JSON y su manejo eficiente de las concesiones \cite{keaDocs}. A
continuación se describe el proceso de implementación.

% -------------------------------------------------------
\subsection{Arquitectura del sistema}

El servicio se desplegó de manera centralizada sobre el servidor Debian de la
red local \texttt{192.168.0.0/24}. Para que el servidor DHCP sea el único que
otorgue direcciones, se desactivó el servicio DHCP del router de la red,
evitando así que dos servidores respondan a las peticiones \textsc{Discover}
de los clientes con ofertas distintas.

La red se dividió en dos segmentos lógicos según la política del proyecto:

\begin{itemize}
  \item \textbf{Equipos de rol (192.168.0.1--192.168.0.109):} incluye al
        router, al propio servidor Debian (\texttt{192.168.0.105}) y a todos
        los servicios (DNS, web, archivos, correo) que requieren una dirección
        IP fija.
  \item \textbf{Equipos de usuario (192.168.0.110--192.168.0.254):} rango de
        direcciones que el servidor DHCP puede entregar dinámicamente a los
        dispositivos de los usuarios de la red.
\end{itemize}

El servidor DHCP entrega a cada cliente, junto con la dirección IP, la
máscara de subred (\texttt{255.255.255.0}), la puerta de enlace
(\texttt{192.168.0.1}), el servidor DNS del proyecto
(\texttt{192.168.0.105}) y el dominio de búsqueda (\texttt{sudoers.lan}).
De esta manera, el cliente queda configurado sin intervención manual y puede
resolver los nombres de los servicios internos inmediatamente.

\subsection{Instalación del servidor DHCP}

El servidor DHCP se instaló sobre el sistema Debian mediante el administrador
de paquetes APT. Kea se distribuye en paquetes separados por protocolo; para
este proyecto se requiere únicamente el servicio DHCPv4:

\begin{lstlisting}[style=terminal]
$ apt update
$ apt install -y kea-dhcp4-server
\end{lstlisting}

El paquete \texttt{kea-dhcp4-server} instala el binario
\texttt{kea-dhcp4}, crea el usuario de sistema \texttt{\_kea} con el que el
servicio ejecuta y registra la unidad de \texttt{systemd}
\texttt{kea-dhcp4-server.service}. Después de la instalación, la
configuración principal queda en \texttt{/etc/kea/kea-dhcp4.conf}.

% -------------------------------------------------------
\subsection{Configuración del servidor}

La configuración de Kea se define en el archivo
\texttt{/etc/kea/kea-dhcp4.conf}, con formato JSON. A continuación se
describen los bloques más relevantes configurados para el proyecto.

\capturaAPA{fig:captura-dhcp-conf}{Archivo de configuración \texttt{/etc/kea/kea-dhcp4.conf} con la definición de la subred, el ámbito y las opciones de red}{captura-dhcp-conf.png}{Captura de pantalla del archivo de configuración de Kea mostrando el bloque \texttt{subnet4} con el ámbito dinámico, el servidor DNS, el dominio y la puerta de enlace definidos.}

\subsubsection{Interfaz y base de datos de concesiones}

Kea escucha en todas las interfaces del servidor para poder atender los
paquetes \textsc{Discover} que llegan por broadcast desde la LAN. Las
concesiones se almacenan en el archivo
\texttt{/var/lib/kea/kea-leases4.csv}:

\begin{lstlisting}[style=terminal]
"interfaces-config": { "interfaces": ["*"] },
"lease-database": { "type": "memfile", "lfc-interval": 3600 }
\end{lstlisting}

La opción \texttt{lfc-interval} indica cada cuántos segundos se compacta el
archivo de concesiones para mantenerlo eficiente.

\subsubsection{Subred, ámbito y opciones}

Se definió la subred \texttt{192.168.0.0/24} con un único ámbito de
asignación dinámica comprendido entre \texttt{192.168.0.110} y
\texttt{192.168.0.254}:

\begin{lstlisting}[style=terminal]
"subnet4": [{
  "subnet": "192.168.0.0/24",
  "pools": [{ "pool": "192.168.0.110 - 192.168.0.254" }],
  "option-data": [
    { "name": "domain-name-servers", "data": "192.168.0.105" },
    { "name": "domain-name", "data": "sudoers.lan" },
    { "name": "routers", "data": "192.168.0.1" }
  ]
}]
\end{lstlisting}

La separación del rango es intencional: los equipos de rol usan direcciones
inferiores a \texttt{192.168.0.110} (fijas o configuradas fuera del ámbito),
mientras que el ámbito dinámico atiende exclusivamente a los equipos de
usuario. Además, cada cliente recibe automáticamente el servidor DNS del
proyecto (\texttt{192.168.0.105}), el dominio \texttt{sudoers.lan} y la
puerta de enlace \texttt{192.168.0.1}.

% -------------------------------------------------------
\subsection{Desactivación del DHCP del router}

El router de la red contaba con su propio servicio DHCP activo, lo que
provocaría un conflicto: tanto el router como Kea responderían a los
paquetes \textsc{Discover} y los clientes podrían recibir configuraciones
distintas e inconsistentes. Para garantizar que el único servidor DHCP de la
red sea el implementado en el proyecto, se accedió a la interfaz de
administración del router y se deshabilitó el servicio DHCP en la LAN
(DHCP Server - Off), manteniendo únicamente la configuración de la puerta de
enlace y las reglas de red existentes.

Al realizar esta desactivación, los clientes conectados a la red que tuvieran
una IP asignada previamente por el router dependen de renovar su concesión;
una vez que lo hacen, el servidor Kea les asigna una dirección dentro del
ámbito dinámico junto con la configuración de red completa.

\subsection{Verificación del servicio}

Antes de probar con clientes reales se validó la configuración y el estado
del servicio. La sintaxis del archivo de configuración se comprobó con la
opción de prueba de Kea:

\begin{lstlisting}[style=terminal]
$ kea-dhcp4 -t /etc/kea/kea-dhcp4.conf
$ systemctl restart kea-dhcp4-server
$ systemctl status kea-dhcp4-server
\end{lstlisting}

El comando \texttt{kea-dhcp4 -t} devuelve \texttt{Configuration check
successful} si el archivo es válido. Posteriormente se reinició el servicio y
se confirmó su estado activo (\texttt{active (running)}) mediante
\texttt{systemctl}. La figura \ref{fig:captura-estado} muestra el estado del

\section{Servidor Web}

\subsection{Arquitectura del servicio}

El servidor web se implementó utilizando Nginx instalado de manera nativa sobre
Debian. Nginx cumple un doble rol estratégico en la infraestructura de la
organización: en primer término, aloja el sitio web institucional estático del
equipo sirviendo páginas HTML5, estilos y recursos gráficos; en segundo
término, actúa como proxy inverso centralizado hacia los diversos servicios
internos que operan en la red local o en puertos internos del sistema (servidor
de impresión CUPS, servicio web de archivos Filebrowser, panel de administración
Portainer y panel de monitoreo Zabbix).

Todo el tráfico web entrante se encuentra protegido mediante el protocolo HTTPS
a través de certificados TLS auto-firmados con soporte para nombres alternativos
(\textit{Subject Alternative Name}, SAN) en formato comodín (\textit{wildcard}).

\subsection{Instalación de paquetes en Debian}

Todos los componentes necesarios para el funcionamiento del servidor web se
instalaron directamente desde los repositorios oficiales de Debian GNU/Linux 12
utilizando el administrador de paquetes APT (\textit{Advanced Package Tool}).

El comando ejecutado para actualizar el índice de repositorios e instalar Nginx
junto con la biblioteca criptográfica OpenSSL fue el siguiente:

\begin{lstlisting}[style=terminal]
$ sudo apt update
$ sudo apt install -y nginx openssl
\end{lstlisting}

La descripción y justificación de cada paquete instalado se detalla a
continuación:

\begin{itemize}
  \item \textbf{nginx}: servidor web de arquitectura orientada a eventos
        altamente escalable, utilizado ampliamente como servidor HTTP y proxy
        inverso debido a su bajo consumo de recursos y alto rendimiento bajo
        cargas concurrentes.
  \item \textbf{openssl}: conjunto de herramientas y librerías criptográficas de
        código abierto indispensables para la generación de claves privadas,
        solicitudes de firma de certificados (CSR) y certificados digitales
        X.509 necesarios para la habilitación del protocolo HTTPS.
\end{itemize}

Tras la instalación en Debian, los archivos de configuración y directorios del
servicio quedan organizados bajo el estándar del sistema de archivos FHS
(\textit{Filesystem Hierarchy Standard}):

\begin{itemize}
  \item \texttt{/etc/nginx/nginx.conf}: archivo principal de directivas globales
        del servidor.
  \item \texttt{/etc/nginx/sites-available/}: directorio que alberga los archivos
        de configuración de los virtual hosts disponibles en el servidor.
  \item \texttt{/etc/nginx/sites-enabled/}: directorio que contiene los enlaces
        simbólicos hacia los archivos de \texttt{sites-available/} que se
        encuentran activos.
  \item \texttt{/var/www/html/}: directorio raíz predeterminado donde se alojan
        los archivos HTML, CSS e imágenes del sitio web.
  \item \texttt{/etc/ssl/certs/} y \texttt{/etc/ssl/private/}: rutas estándar
        donde se almacenan los certificados públicos y las claves privadas
        respectivamente.
\end{itemize}

\subsection{Generación del certificado SSL/TLS con OpenSSL}

Para garantizar la confidencialidad e integridad del tráfico de red entre los
clientes y el servidor, se generó un certificado SSL auto-firmado de 2048 bits
mediante la herramienta \texttt{openssl}. El certificado incluye el nombre base
del dominio (\texttt{sudoers.lan}) y la extensión comodín
(\texttt{*.sudoers.lan}) en el parámetro \texttt{subjectAltName}, permitiendo
proteger simultáneamente el sitio web principal y todos los subdominios de
proxy inverso.

Los comandos ejecutados en el servidor Debian para la preparación de directorios,
generación del par de claves y asignación de permisos de seguridad fueron:

\begin{lstlisting}[style=terminal]
# Crear directorios de certificados con permisos restrictivos
$ sudo mkdir -p /etc/ssl/certs /etc/ssl/private

# Generar clave privada y certificado auto-firmado X.509
$ sudo openssl req -new -x509 -days 3650 -nodes \
    -out /etc/ssl/certs/web.pem \
    -keyout /etc/ssl/private/web.key \
    -subj "/CN=sudoers.lan/O=TSO-II/C=AR" \
    -addext "subjectAltName = DNS:sudoers.lan, DNS:*.sudoers.lan"

# Establecer permisos de seguridad en la clave privada y certificado
$ sudo chmod 600 /etc/ssl/private/web.key
$ sudo chmod 644 /etc/ssl/certs/web.pem
\end{lstlisting}

El significado de los parámetros empleados en la invocación de \texttt{openssl}
comprende:

\begin{itemize}
  \item \texttt{-new -x509}: instruye a la herramienta para generar directamente
        un certificado auto-firmado de acuerdo con la norma ITU-T X.509 en lugar
        de una solicitud de firma (CSR).
  \item \texttt{-days 3650}: define un periodo de vigencia de 10 años para el
        certificado, idóneo para entornos de laboratorio y servidores de red
        interna.
  \item \texttt{-nodes}: (\textit{no DES}) especifica que la clave privada generada
        no debe cifrarse con contraseña, permitiendo que el demonio Nginx se
        inicie de manera desatendida durante el arranque del sistema operativo.
  \item \texttt{-subj}: establece los campos del nombre distinguido (DN),
        asignando \texttt{CN=sudoers.lan} como nombre común y la organización
        \texttt{TSO-II}.
  \item \texttt{-addext}: agrega extensiones X.509 v3, específicamente
        \texttt{subjectAltName}, que define los nombres de dominio cubiertos
        por el certificado.
\end{itemize}

\subsection{Configuración TLS global y parámetros de sesión}

Para asegurar que todas las comunicaciones HTTPS cumplan con los estándares de
seguridad contemporáneos, se establecieron parámetros TLS globales dentro del
bloque \texttt{http} de Nginx (\texttt{/etc/nginx/nginx.conf} o archivo incluido
en \texttt{/etc/nginx/conf.d/tls.conf}):

\begin{lstlisting}[style=terminal]
# Protocolos criptograficos admitidos
ssl_protocols TLSv1.2 TLSv1.3;
ssl_prefer_server_ciphers off;

# Gestion de cache de sesiones TLS
ssl_session_cache shared:SSL:10m;
ssl_session_timeout 1d;
\end{lstlisting}

\subsection{Soporte WebSocket para aplicaciones web interactivas}

Determinadas interfaces de administración, como el panel de gestión Portainer,
requieren el mantenimiento de túneles bidireccionales en tiempo real mediante el
protocolo WebSocket. Para evitar que el proxy inverso cierre o degrade estas
conexiones, se configuró el bloque \texttt{map} a nivel HTTP en
\texttt{nginx.conf}:

\begin{lstlisting}[style=terminal]
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
\end{lstlisting}

Este mecanismo evalúa dinámicamente la presencia de la cabecera HTTP
\texttt{Upgrade} enviada por el navegador: si la solicitud solicita una
conversión a WebSocket, la variable \texttt{\$connection\_upgrade} adopta el
valor \texttt{upgrade}, permitiendo que Nginx conmute el canal de comunicación
de forma transparente.

\subsection{Configuración de Virtual Hosts y Proxies Inversos}

La configuración integral de los sitios virtuales y proxies inversos se plasmó
en el archivo \texttt{/etc/nginx/sites-available/sudoers.conf}, habilitado en el
servidor mediante un enlace simbólico en \texttt{/etc/nginx/sites-enabled/}. A
continuación se documenta la estructura de cada virtual host configurado.

\subsubsection{Proxy inverso para CUPS (Servidor de Impresión)}

El servidor de impresión CUPS atiende en el puerto local 631. Para exponer su
interfaz gráfica en el subdominio \texttt{print.sudoers.lan} bajo HTTPS, se
configuró la redirección obligatoria desde el puerto 80 y la terminación TLS
en el puerto 443:

\begin{lstlisting}[style=terminal]
# Redireccion de trafico plano a HTTPS
server {
    listen 80;
    server_name print.sudoers.lan;
    return 301 https://$host$request_uri;
}

# Proxy inverso con terminacion TLS
server {
    listen 443 ssl;
    server_name print.sudoers.lan;

    ssl_certificate     /etc/ssl/certs/web.pem;
    ssl_certificate_key /etc/ssl/private/web.key;

    location / {
        proxy_pass http://127.0.0.1:631;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
\end{lstlisting}

\subsubsection{Proxy inverso para Filebrowser (Servidor de Archivos Web)}

El servidor de archivos Filebrowser ofrece una interfaz web de gestión y
transferencia de ficheros. Dado que los usuarios requieren cargar archivos de gran
tamaño, se amplió la directiva \texttt{client\_max\_body\_size} a 500\,MB:

\begin{lstlisting}[style=terminal]
server {
    listen 80;
    server_name files.sudoers.lan;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name files.sudoers.lan;

    ssl_certificate     /etc/ssl/certs/web.pem;
    ssl_certificate_key /etc/ssl/private/web.key;

    client_max_body_size 500M;

    location / {
        proxy_pass http://127.0.0.1:8082;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
\end{lstlisting}

\subsubsection{Proxy inverso para Portainer (Panel de Administración)}

Para el panel de administración Portainer (puerto 9000), se implementó el paso
de parámetros para WebSocket junto con temporizadores de lectura y envío
extendidos a 3600 segundos (1 hora), garantizando sesiones interactivas estables
sin desconexiones prematuras:

\begin{lstlisting}[style=terminal]
server {
    listen 80;
    server_name portainer.sudoers.lan;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name portainer.sudoers.lan;

    ssl_certificate     /etc/ssl/certs/web.pem;
    ssl_certificate_key /etc/ssl/private/web.key;

    location / {
        proxy_pass http://127.0.0.1:9000;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;

        # Parametros para tunelizacion WebSocket
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600;
        proxy_send_timeout 3600;
    }
}
\end{lstlisting}

\subsection{Virtual host del sitio principal y servidor por defecto}

El sitio web institucional del proyecto se publica como contenido estático
alojado en el directorio \texttt{/var/www/html/}. Responde a las peticiones
dirigidas a \texttt{web.sudoers.lan}, \texttt{www.sudoers.lan} y
\texttt{sudoers.lan}:

\begin{lstlisting}[style=terminal]
server {
    listen 80;
    server_name web.sudoers.lan www.sudoers.lan sudoers.lan;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name web.sudoers.lan www.sudoers.lan sudoers.lan;

    ssl_certificate     /etc/ssl/certs/web.pem;
    ssl_certificate_key /etc/ssl/private/web.key;

    root /var/www/html;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
\end{lstlisting}

Para el despliegue del sitio, los archivos HTML, CSS y recursos gráficos se
copiaron directamente al directorio raíz del servidor web en Debian, asignando la
propiedad al usuario y grupo del sistema \texttt{www-data}:

\begin{lstlisting}[style=terminal]
$ sudo cp -r services/web/public/* /var/www/html/
$ sudo chown -R www-data:www-data /var/www/html
$ sudo chmod -R 755 /var/www/html
\end{lstlisting}

Adicionalmente, se implementó el bloque \texttt{default\_server} para gestionar
de forma controlada cualquier conexión que ingrese directamente mediante la
dirección IP del servidor o a través de dominios no contemplados:

\begin{lstlisting}[style=terminal]
server {
    listen 80 default_server;
    server_name _;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl default_server;
    server_name _;

    ssl_certificate     /etc/ssl/certs/web.pem;
    ssl_certificate_key /etc/ssl/private/web.key;

    root /var/www/html;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
\end{lstlisting}

\subsection{Gestión del servicio con systemd y control de firewall}

La habilitación, supervisión y administración del servicio Nginx en Debian se
efectúa a través del sistema de inicio y control de procesos \texttt{systemd}.

Antes de iniciar o recargar el servicio, se ejecutó la comprobación sintáctica de
los archivos de configuración mediante el comando de validación de Nginx:

\begin{lstlisting}[style=terminal]
$ sudo nginx -t
nginx: the configuration file /etc/nginx/nginx.conf syntax is ok
nginx: configuration file /etc/nginx/nginx.conf test is successful
\end{lstlisting}

Una vez verificada la corrección sintáctica, se habilitó y arrancó el servicio
del sistema:

\begin{lstlisting}[style=terminal]
# Habilitar el servicio para arranque automatico al encender el equipo
$ sudo systemctl enable nginx

# Iniciar o reiniciar el demonio
$ sudo systemctl restart nginx

# Inspeccionar el estado operativo del servicio
$ sudo systemctl status nginx
\end{lstlisting}
