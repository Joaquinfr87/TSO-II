\section{Desarrollo del trabajo}

Este capítulo documenta el proceso de configuración del servidor web del
proyecto sobre Debian. Se describe desde la instalación del servicio hasta
las pruebas de acceso realizadas desde los clientes.

% -------------------------------------------------------
\subsection{Arquitectura del servicio}

El servidor web se implementó utilizando Nginx 1.27 sobre Alpine Linux,
desplegado como un contenedor Docker. Nginx cumple un doble rol en el
proyecto: sirve el sitio web estático del equipo y actúa como proxy inverso
hacia los servicios internos de la infraestructura, todo protegido con HTTPS
mediante certificados auto-firmados.

El servidor opera como punto de entrada único para el acceso HTTP/HTTPS
de todos los servicios del proyecto. La figura \ref{fig:arquitectura-web}
presenta la arquitectura general.

\subsection{Instalación del servicio}

El servidor web se despliega como un contenedor Docker basado en
\texttt{nginx:1.27-alpine}. El Dockerfile instala \texttt{openssl} como
dependencia adicional para la generación de certificados:

\begin{lstlisting}[style=terminal]
FROM nginx:1.27-alpine

RUN apk add --no-cache openssl

COPY nginx.conf /etc/nginx/conf.d/default.conf
COPY public/ /usr/share/nginx/html/
COPY entrypoint.sh /entrypoint.sh
RUN chmod +x /entrypoint.sh

EXPOSE 80 443

ENTRYPOINT ["/entrypoint.sh"]
CMD ["nginx", "-g", "daemon off;"]
\end{lstlisting}

\subsection{Generación automática de certificados SSL/TLS}

El script \texttt{entrypoint.sh} genera un certificado SSL auto-firmado al
iniciar el contenedor, si no existe uno previo. El certificado cubre el
dominio base y todos los subdominios mediante un \textit{wildcard} en el
\texttt{subjectAltName}:

\begin{lstlisting}[style=terminal]
#!/bin/sh
set -e

DOMAIN="${WEB_DOMAIN:-sudoers.lan}"

SSL_DIR="/etc/ssl"
CERT_FILE="${SSL_DIR}/certs/web.pem"
KEY_FILE="${SSL_DIR}/private/web.key"

if [ ! -f "$CERT_FILE" ]; then
    echo ">>> Generando certificado SSL auto-firmado para ${DOMAIN}..."
    mkdir -p "${SSL_DIR}/certs" "${SSL_DIR}/private"
    openssl req -new -x509 -days 3650 -nodes \
        -out "$CERT_FILE" \
        -keyout "$KEY_FILE" \
        -subj "/CN=${DOMAIN}/O=TSO-II/C=AR" \
        -addext "subjectAltName = DNS:${DOMAIN}, DNS:*.${DOMAIN}" \
        2>/dev/null
    chmod 600 "$KEY_FILE"
    echo ">>> Certificado generado: ${CERT_FILE}"
else
    echo ">>> Certificado SSL ya existe, omitiendo generacion"
fi

exec "$@"
\end{lstlisting}

\subsection{Soporte WebSocket para Portainer}

Portainer requiere conexiones WebSocket para la interacción en tiempo real con
la interfaz de gestión. Nginx implementa este soporte mediante un bloque
\texttt{map} que transforma las cabeceras de actualización:

\begin{lstlisting}[style=terminal]
map $http_upgrade $connection_upgrade {
    default upgrade;
    ''      close;
}
\end{lstlisting}

Este bloque asigna el valor \texttt{upgrade} a la variable
\texttt{\$connection\_upgrade} cuando el cliente envía la cabecera
\texttt{Upgrade} (típica de WebSocket), y \texttt{close} en caso contrario.

\subsection{Configuración de los proxies inversos}

Cada servicio interno del proyecto se expone a través de un subdominio con
redirección HTTP a HTTPS y resolución dinámica del upstream. A continuación
se documenta la configuración de cada proxy.

\subsubsection{Proxy inverso para CUPS (Impresión)}

El servidor de impresión CUPS se expone en \texttt{print.sudoers.lan}:

\begin{lstlisting}[style=terminal]
server {
    listen 80;
    server_name print.sudoers.lan;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name print.sudoers.lan;

    ssl_certificate     /etc/ssl/certs/web.pem;
    ssl_certificate_key /etc/ssl/private/web.key;

    location / {
        resolver 127.0.0.11 valid=10s ipv6=off;
        set $cups_upstream http://tso-print:631;
        proxy_pass $cups_upstream;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
\end{lstlisting}

\subsubsection{Proxy inverso para Filebrowser (Archivos)}

El servicio de archivos Filebrowser se expone en \texttt{files.sudoers.lan}
con un límite de subida de 500\,MB:

\begin{lstlisting}[style=terminal]
server {
    listen 443 ssl;
    server_name files.sudoers.lan;

    ssl_certificate     /etc/ssl/certs/web.pem;
    ssl_certificate_key /etc/ssl/private/web.key;

    client_max_body_size 500M;

    location / {
        resolver 127.0.0.11 valid=10s ipv6=off;
        set $files_upstream http://tso-files:80;
        proxy_pass $files_upstream;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
    }
}
\end{lstlisting}

\subsubsection{Proxy inverso para Portainer (Gestión Docker)}

Portainer se expone en \texttt{portainer.sudoers.lan} con soporte WebSocket
y timeouts extendidos de 1 hora:

\begin{lstlisting}[style=terminal]
server {
    listen 443 ssl;
    server_name portainer.sudoers.lan;

    ssl_certificate     /etc/ssl/certs/web.pem;
    ssl_certificate_key /etc/ssl/private/web.key;

    location / {
        resolver 127.0.0.11 valid=10s ipv6=off;
        set $portainer_upstream http://tso-portainer:9000;
        proxy_pass $portainer_upstream;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_http_version 1.1;
        proxy_set_header Upgrade $http_upgrade;
        proxy_set_header Connection $connection_upgrade;
        proxy_read_timeout 3600;
        proxy_send_timeout 3600;
    }
}
\end{lstlisting}

\subsubsection{Técnica de resolución dinámica de upstreams}

Todos los bloques de proxy inverso comparten una técnica fundamental: la
resolución dinámica del upstream mediante una variable y el resolver interno
de Docker:

\begin{lstlisting}[style=terminal]
resolver 127.0.0.11 valid=10s ipv6=off;
set $upstream http://nombre-contenedor:puerto;
proxy_pass $upstream;
\end{lstlisting}

\subsection{Virtual host del sitio principal}

El sitio web del proyecto se sirve como contenido estático desde
\texttt{/usr/share/nginx/html}, respondiendo a tres nombres de dominio:

\begin{lstlisting}[style=terminal]
server {
    listen 80;
    server_name web.sudoers.lan www.sudoers.lan sudoers.lan;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl;
    server_name web.sudoers.lan www.sudoers.lan sudoers.lan;

    ssl_certificate     /etc/ssl/certs/web.pem;
    ssl_certificate_key /etc/ssl/private/web.key;

    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
\end{lstlisting}

El contenido estático se monta como volumen de solo lectura desde el host,
lo que permite actualizar la página sin reconstruir la imagen:

\begin{lstlisting}[style=terminal]
volumes:
  - ${WEB_SITE_DIR:-./services/web/public}:/usr/share/nginx/html:ro
\end{lstlisting}

\subsection{Servidor por defecto}

El servidor por defecto captura cualquier petición que llegue por IP directa
o por un dominio no declarado en la configuración:

\begin{lstlisting}[style=terminal]
server {
    listen 80 default_server;
    server_name _;
    return 301 https://$host$request_uri;
}

server {
    listen 443 ssl default_server;
    server_name _;

    ssl_certificate     /etc/ssl/certs/web.pem;
    ssl_certificate_key /etc/ssl/private/web.key;

    root /usr/share/nginx/html;
    index index.html;

    location / {
        try_files $uri $uri/ =404;
    }
}
\end{lstlisting}

El bloque \texttt{default\_server} garantiza que ninguna petición HTTP quede
sin respuesta, redirigiendo siempre a HTTPS y mostrando el sitio principal.
